## 二、Critical问题（必须修复）

### 2.1 监测平台UI与后端数据结构不匹配

**问题描述**:
监测平台的Web UI（`monitor_platform/server.py`中的`DASHBOARD_HTML`）期望接收的数据结构与后端实际发送的数据结构不一致。

**UI期望的数据结构**:
```javascript
function addInspection(data) {
    const crackCount = data.crack?.details?.length || 0;
    const tempStatus = data.temperature?.status || 'NORMAL';
    const tempValue = (data.temperature?.value || 0).toFixed(1);
    // ...
}
```

**后端实际发送的数据结构**:
```python
{
    "type": "inspection_result",
    "data": {
        "id": "INS_1234567890",
        "timestamp": 1234567890.0,
        "datetime": "2026-08-20 10:00:00",
        "device_id": "LITE3-001",
        "data": {  # 这是payload
            "defect_type": "crack",
            "subtype": "longitudinal",
            "measurements": {"width_mm": 0.15, "length_mm": 45.2},
            "confidence": 0.92,
            # ...
        }
    }
}
```

**影响**:
- UI无法正确显示巡检结果表格
- 温度状态和裂缝数量显示为空或错误值
- 演示时用户会看到空白或不正确的数据

**修复方案**:
需要修改`monitor_platform/server.py`中的`process_message`方法，确保广播给前端的数据结构与UI期望的一致：
```python
# 修改前
await self.broadcast({
    "type": "inspection_result",
    "data": result
})

# 修改后 - 需要转换数据结构
await self.broadcast({
    "type": "inspection_result",
    "data": {
        "crack": {
            "detected": True,
            "count": len(payload.get('measurements', {})),
            "details": [...]  # 从payload中提取
        },
        "temperature": {
            "status": payload.get('alert_level', 'NORMAL'),
            "value": payload.get('temperature', {}).get('max_c', 0)
        }
    }
})
```

### 3.2 演示流程与12分钟要求不符

**问题描述**:
当前演示流程时长约20秒，与国赛要求的12分钟演示流程差距巨大。

**当前流程**:
```python
# src/app/main.py
await _demo_stand_up(controller)      # 3s
await asyncio.sleep(2)                # 2s
await _demo_ptz_scan(ptz)             # ~3s
await asyncio.sleep(1)                # 1s
await _demo_crack_detection(...)      # 2s
await asyncio.sleep(2)                # 2s
await _demo_temperature_monitor(...)  # 5s
await asyncio.sleep(2)                # 2s
await _demo_move_forward(...)         # 2s
await asyncio.sleep(2)                # 2s
await _demo_return(...)               # 2s
await asyncio.sleep(2)                # 2s
await _demo_stand_down(...)           # 2s
# 总计: ~24秒
```

**官方要求**:
根据《感知开发手册V2.2.3》，标准演示流程应包含：
1. 初始检测（约2分钟）
2. 持续巡检（约6分钟）
3. 异常上报（约2分钟）
4. 系统自检（约2分钟）

**影响**:
- 演示时间不足，无法展示完整功能
- 评委可能质疑系统可靠性

**修复方案**:
1. 实现完整的12分钟演示脚本（`scripts/demo_script.py`）
2. 使用`SimulationDataGenerator`的`scripted`模式生成预设数据
3. 添加航点间移动时间（实际距离/速度）
4. 添加检测等待时间（模拟AI推理耗时）

**文档声明**:
- `data/logs/app_YYYY-MM-DD.log`

- `data/logs/demo_YYYY-MM-DD.log`

**代码实现**:

# src/app/main.py
logger.add("data/logs/app_{time:YYYY-MM-DD}.log", ...)

**影响**: 低，不会导致功能失败，但可能影响问题排查。

### 4.3 缺少配置文件验证

**现状**:
- `config/inspection_config.yaml`已创建
- 但没有 Schema 验证
- 如果配置字段缺失或类型错误，运行时才会报错

**建议**:
```python
# 添加配置验证
from pydantic import BaseModel, validator

class RobotConfig(BaseModel):
    ip: str
    port: int
    
    @validator('port')
    def port_range(cls, v):
        if not (0 < v < 65536):
            raise ValueError('Port must be 1-65535')
        return v
```

## 五、用户操作流程障碍分析

### 5.1 典型用户路径

```
用户流程:
1. 克隆仓库 → git clone ...
2. 安装依赖 → pip install -r requirements.txt
3. 配置网络 → 设置WiFi热点，配置IP

### 5.2 潜在障碍识别

| 步骤 | 障碍 | 可能性 | 严重程度 | 解决方案 |
|------|------|--------|----------|----------|
| 安装依赖 | 缺少CUDA/TensorRT | 高 | 🟡 中 | 提供Docker镜像 |

| 查看结果 | UI数据不显示 | **高** | 🔴 高 | **修复数据结构匹配** |

### 5.3 最可能失败的场景

**场景1: 首次部署（云端环境）**
```
用户操作: python3 scripts/start_monitor.py

原因: UI与后端数据结构不匹配
解决: 修复monitor_platform/server.py中的数据转换逻辑
```

**场景3: 真实模式切换**
```
用户操作: python3 scripts/run_demo.py --mode real
预期结果: 使用真实模型推理
实际结果: ❌ 模型文件不存在，自动降级到模拟模式
